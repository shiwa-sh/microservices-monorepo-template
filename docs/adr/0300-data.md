# ADR-0300: Data & Migrations

- **Status:** Accepted
- **Date:** 2026-08-06
- **Deciders:** Platform team
- **Related:** [ADR-0000](0000-platform-foundations.md), [ADR-0100](0100-language-and-runtime.md), [ADR-0200](0200-cluster-topology.md), [ADR-0201](0201-gitops.md), [ADR-0202](0202-secrets.md), [ADR-0301](0301-data-lifecycle-privacy.md), [ADR-0302](0302-temporal.md), [ADR-0303](0303-api-contracts-and-lifecycle.md), [ADR-0304](0304-identity-and-authorization.md)

## Context

Every backend service needs persistent state. This ADR answers engine, operation, schema evolution, service access, and parity in one place.

Several platform components already require Postgres: Kratos and Hydra, OpenFGA, and Temporal. A second engine for application services would mean operating two.

Authz-relevant mutations are workflows ([ADR-0302](0302-temporal.md)), so the database needs no built-in outbox.

## Decision drivers

1. **One engine.** Polyglot persistence is a permanent operational tax multiplied by the service count ([ADR-0000](0000-platform-foundations.md)).
2. **Service-owned data.** A service's data is private; other services read it only through that service's HTTP API ([ADR-0000](0000-platform-foundations.md), principle 10).
3. **Schemas as code in the repo.** Migrations are SQL files in the service folder, code-reviewed.
4. **Parity.** Whatever produces a working database in production works locally with one command.
5. **No extension becomes tribal knowledge.** Extensions are per-service decisions recorded in the service README.

## Considered options

### Engine

| Option | Already required by the platform | Verdict |
| --- | --- | --- |
| **PostgreSQL** | **yes** — Kratos, Hydra, OpenFGA, Temporal | **Chosen.** Strong consistency, transactional DDL, mature replication and backup tooling, an extension ecosystem covering anticipated needs, and the best Go driver with first-class sqlc support |
| MySQL / MariaDB | no | Adds a second engine to operate for no capability gained |
| A document store beside Postgres | no | Polyglot persistence pays operational cost per engine, against driver 1. `jsonb` covers the cases that motivate it |

### Cluster operator

| Option | Kubernetes-native CRDs | Pooler included | Verdict |
| --- | --- | --- | --- |
| **CloudNativePG** | `Cluster`, `Pooler`, `Backup`, `ScheduledBackup` | **yes**, as a CRD | **Chosen.** A single-binary operator, HA via streaming replication, failover and switchover as CRD operations, backups to object storage with PITR via Barman. Apache-2.0, CNCF |
| Zalando postgres-operator | yes | separate | Mature, and its configuration surface is larger for the same capability |
| Crunchy PGO | yes | separate | Capable, with a heavier component set |
| StackGres | yes | yes | Broadest feature set and the largest operational surface of the four |
| Raw Patroni | **no** — not Kubernetes-native | no | Every CRD operation above becomes a runbook |

### SQL access

| Option | Query plans visible | Runtime cost | Verdict |
| --- | --- | --- | --- |
| **sqlc + pgx** | **yes — you write the SQL** | none; generated Go | **Chosen** |
| GORM, ent, bun | hidden behind an abstraction | reflection or builder overhead | Hiding query plans becomes a liability exactly when load makes them matter |
| `database/sql` by hand | yes | none | sqlc produces the same thing with types, for free |

## Decision

### Topology: one logical database per service, one shared cluster

| Rule | Consequence |
| --- | --- |
| Service A cannot connect to service B's database | Credentials are per service |
| No cross-database queries | Cross-service data needs go over HTTP ([ADR-0303](0303-api-contracts-and-lifecycle.md)) |
| One shared physical cluster | Operational cost stays proportional to clusters, not services. Read replicas arrive when single-service load justifies them |
| Compliance isolation earns its own cluster | Never its own schema in the shared cluster |

### Connection pooling: PgBouncer in transaction mode

Deployed through CNPG's `Pooler` CRD, between every service and the cluster.

- **Transaction mode is the default.** Session-mode features — advisory locks, `SET LOCAL`, cross-statement `LISTEN/NOTIFY`, server-side prepared statements without compatibility flags — are not permitted in application code.
- `pgx` is configured for PgBouncer compatibility (`statement_cache_mode = describe`).
- Per-service connection limits are sized in PgBouncer, not in `pgx`. The app-side pool is small per replica, and PgBouncer multiplexes onto a smaller server-side pool.

**Seam:** a second `Pooler` in session mode is not provisioned by default. **Trigger:** a workload genuinely needs `LISTEN/NOTIFY`-driven behaviour. **Cost if adopted late:** none — it is added cluster-wide at that point, with a justification in the service README.

### Migrations: dbmate

Files live at `services/<service>/migrations/<YYYYMMDDHHMMSS>_<description>.sql`, one SQL file with `-- migrate:up` and `-- migrate:down` sections.

**Down migrations are not used in production.** Production rollback is a forward fix — a new migration reversing the change. Down sections exist for local development.

| Environment | How they run |
| --- | --- |
| Production | `dbmate up` as an **init container** before the service container in the shared chart ([ADR-0201](0201-gitops.md)). The service starts only after it succeeds, and an advisory lock prevents concurrent runs across replicas |
| Local | the same binary against the local database, via `mise run db:migrate` |

The init container image is the one engineers run locally. There is no separate migration image to drift.

SQL is linted by **sqruff** — a single Rust binary, sqlfluff-compatible, reading `.sqlfluff` with `dialect = postgres` — on both queries and migrations, at pre-commit and in CI. It needs no Python toolchain ([ADR-0100](0100-language-and-runtime.md)).

### The OpenFGA schema is a seed Job

Not SQL, and the same class of problem: a declarative schema that must be applied before consumers rely on it.

An idempotent, Argo-synced Job in the OpenFGA chart runs a sync wave after the Deployment is Ready. It writes the canonical schema and touches the **static** ops-policy grants. Both operations are idempotent, so the Job is safe on every sync, and local and deployed environments share one seeding path.

Per-human operator membership is **not** baked in here; it is runtime state managed by `mise run ops:grant` ([ADR-0306](0306-trust-tiers-and-urls.md)).

### Zero-downtime schema changes: expand, migrate, contract

1. **Expand.** Add columns or tables, nullable or defaulted. Deploy.
2. **Migrate data.** Backfills run as **Temporal workflows** ([ADR-0302](0302-temporal.md)), not SQL scripts, so they are observable, resumable, and rate-limitable. Deploy if application code needs new behaviour.
3. **Contract.** Drop old columns or tables only once no code references them.

| Hard rule | Reason |
| --- | --- |
| No destructive migration in the same deploy as code using the new schema | At least one deploy boundary must separate expand from the code switch |
| No long-lock `ALTER TABLE` without `lock_timeout` and a documented online-DDL plan | A long lock is an outage, and it is blocked at review |
| No `DROP COLUMN` until code has shipped without referencing it for one full production deploy cycle | The rollback target must still work |

### Multi-tenancy is row-level

Every multi-tenant table carries an `org_id` column and service code filters by the value from the request context. **Row-Level Security** is enabled on those tables, keyed on `CURRENT_SETTING('app.org_id')`, set per request through `pgx`'s `BeforeAcquire` hook.

RLS is enabled per service the first time that service becomes multi-tenant. It is not a day-one default.

Schema-per-tenant and database-per-tenant are not used: they explode the migration matrix. A tenant requiring physical isolation earns its own service, and possibly its own cluster.

### Extensions

| Tier | Extensions | How they arrive |
| --- | --- | --- |
| Cluster default | `pgcrypto`, `uuid-ossp`, `pg_stat_statements` | pre-allowed in the cluster manifest; common enough to be cheap |
| Sanctioned per service | PostGIS, TimescaleDB, pgvector | the first service that needs one installs it in a migration, records it in its README, and the extension joins the cluster's pre-allow list |
| Anything else | — | requires an ADR |

### Credentials and backups

Each service has a dedicated Postgres role with access only to its own database. Roles, grants, and passwords live in a SOPS-encrypted file ([ADR-0202](0202-secrets.md)) that the operator materialises as Secrets the chart mounts. The local connection string is committed in `.env.example` with non-secret defaults.

Backups are [ADR-0200](0200-cluster-topology.md)'s: CNPG writes to the off-cluster bucket with WAL-based PITR, and the restore is rehearsed quarterly. There are no service-specific exceptions.

### Major-version upgrades

A new `Cluster` is created at the new version, CNPG replicates from the old, and traffic cuts over with a brief read-only window per service. Performed once per Postgres release cadence during a planned maintenance window, per [`docs/database/major-upgrade.md`](../database/major-upgrade.md).

## Consequences

### Positive

- One engine, one mental model.
- Service ownership is structural: a service cannot read another's data even if it tried.
- Migrations live with the code they describe, so one diff carries behaviour and schema together.
- Local matches production: the same binary, the same SQL, the same init-container shape.
- Backfills as workflows make zero-downtime schema change a normal review item rather than an event.

### Negative / Risks

- **Transaction mode rules out a narrow set of Postgres features.** Mitigated by lint and the session-mode seam.
- **A shared physical cluster means a noisy neighbour affects every service.** Mitigated by CNPG resource isolation, per-role slow-query alerting, and per-service connection limits.
- **No ORM is unfamiliar** to engineers arriving from Django, Rails, or Spring. Paid once, during onboarding.
- **Forward-fix as the only rollback path requires discipline.** Documented in `docs/database/migrations.md`.
- **RLS is opt-in per service**, so a service that becomes multi-tenant without enabling it has tenant isolation only in application code. The `org_id` column is the visible marker a reviewer checks against.

## Rules

- Every service uses Postgres. Another engine requires its own ADR. `(review-only)`
- Each service owns exactly one logical database, with credentials scoped to it. Cross-database queries are not used. `(review-only)`
- Cross-service data access is HTTP through the generated OpenAPI client. `(CI: ci-lint)`
- The cluster is operated by CloudNativePG, with pooling through a transaction-mode `Pooler`. `(review-only)`
- Application code is transaction-mode safe: no advisory locks, no `SET LOCAL`, no cross-statement `LISTEN/NOTIFY`, and no server-side prepared statements without compatibility flags. `(CI: lint:sql)`
- SQL access is sqlc plus pgx. ORMs are not used. `(CI: ci-lint)`
- Migration files live at `services/<service>/migrations/` and are managed by dbmate. `(CI: lint:service-contract)`
- Migrations run as the service's init container in production, and the same binary runs locally. `(review-only)`
- Down migrations are local-only. Production rollback is a forward fix. `(review-only)`
- Schema changes follow expand, migrate as a Temporal workflow, then contract, with at least one production deploy boundary between expand and the code switch. `(review-only)`
- A multi-tenant service's tenant tables carry `org_id` and have RLS enabled keyed on `app.org_id`. `(review-only)`
- Sanctioned extensions are PostGIS, TimescaleDB, and pgvector, plus the cluster default set. Others require an ADR. `(review-only)`
- Database credentials reach pods through the sops-operator from encrypted files. `(CI: lint:secrets)`
